# 背光版本对比与故障归因

## 当前验证状态

2026-10-21，用户在安装依赖修正版后确认“亮度调节正常”。该版产物 UUID 为 `FA126DDD-CFB3-326A-8905-0CA7C7E72F91`，SHA-256 为 `e6cbd57e701f34b07673e9928dc8e5dd60476a6c67c99cb07c48537f62fd5851`。这是用户实机反馈，本轮没有再次执行系统亮度查询、WMI 测试或读取活动驱动 UUID；长期稳定性、睡眠唤醒和各供电状态尚未验证。

对比基线为提交 `25b60d79f6892fd5cf0a1d5d07519b3227d58605`。早期 EC 补丁取自原工作区 `build/ec-backlight-{registry-v2,dispatch-v3,wmi-v4}-20261020/source/` 的构建快照；当前实现位于独立工作区 `ec-backlight-rewrite`。不能把原工作区尚未整理的旧 `Backlight.cpp` 当作当前安装源码。

## 三类症状需要分别解释

| 症状 | 目前可以成立的结论 | 不能成立的结论 |
| --- | --- | --- |
| 干净基线启动初期有效，之后滑块动而亮度不变 | 原生背光路径不能覆盖本机用户观察到的全部运行状态；WMI EC 在已测试桌面状态可以改变物理亮度 | 已查明由某个 NVIDIA 驱动在固定时刻接管 |
| 早期 EC 补丁安装后调亮度或运行查询时整机卡住 | 旧代码存在混用 AMD 路径、回调取锁、共享状态同步不完整等问题；现版消除了这些耦合 | 已取得死锁栈，证明某一把锁或某次 WMAA 调用导致全部卡死 |
| 独立服务重写后，一出现进度条便重启 | 构建存在类导出缺失和 ACPI 直接依赖缺失；只补类导出仍失败，补正确依赖后用户确认启动及调光正常 | 最后一次依赖修改本身修复了旧版运行时所有潜在死锁 |

## 原生背光与 EC 补丁的差异

基线 `Backlight::wrapSetAttributeForConnection` 先调用 AMD 原 `setAttributeForConnection`，随后根据链路能力调用 `dc_link_set_backlight_level` 或 `dc_link_set_backlight_level_nits`。这是 GPU 的背光路径，不访问本机 `AWMI.WMAA`。

本机 WMI 接口则通过固件写 EC 的 `PCBV`，再置 `SPBL=1`。独立模块此前完成 264 → 132 → 264，用户确认屏幕变暗再恢复。当前用户反馈又验证了系统滑块到该后端的整条路径。由此可知本机需要覆盖 EC 路径，但尚不能确定基线失效的具体交接节点。

## 旧 EC 补丁与当前实现

| 环节 | 旧 EC 补丁 | 当前实现 |
| --- | --- | --- |
| 亮度写入 | v2 总是先执行 AMD 原 SET；v3/v4 将 EC 分支提前，但首次同值、未就绪或错误回退时仍可能走 AMD | EC 后端就绪后，SET 直接提交原子请求；后端故障时返回错误，不静默退回 AMD |
| 亮度读取 | v2/v3/v4 都先调用 AMD 原 GET，随后才用软件缓存覆盖结果 | EC 后端就绪后直接读取原子缓存，GET 不进入 AMD，也不读取 WMI |
| 回调与工作线程通信 | 回调执行 `IOLockLock`、写共享值和 `IOLockWakeup` | 回调只使用无锁原子读写；独立工作循环每 100 ms 消费最新请求 |
| 设备发现与生命周期 | 工作线程在首个请求时自行遍历注册表、寻找 WMI 设备并初始化 | IOKit 匹配 WMI provider，保留设备；显示参数有效后在自己的工作循环中初始化 |
| 状态共享 | `ecReady`、当前亮度和量程等跨线程访问并未统一使用原子同步 | 状态使用原子发布；亮度和量程装入同一个 64 位请求，避免读取到不同请求的组合 |
| 亮度换算 | 先转换为整数百分比，再转换为 EC 范围，丢失细节 | 用 64 位中间值直接从原始范围映射到 EC 范围 |
| 诊断 | 启用 trace 时在工作线程中进行内核文件写入及同步刷盘 | 调光路径不写文件 |

## 为什么这些差异可能影响整机响应

显示驱动回调可能处于显示栈自己的串行化上下文。如果回调再取额外的互斥锁，或继续调用一个已经不适用于面板控制状态的 AMD 处理路径，就增加了显示栈等待、重入和不同控制路径相互影响的机会。当前实现把回调缩小为发布数值，并将固件执行与显示回调分开，移除了这些耦合。

这是根据代码结构作出的风险分析，不是已捕获的死锁链。尤其需要保留以下事实：

- 旧版已经有异步 EC 工作线程，不能说它把所有 WMI 调用都同步放在显卡回调里。
- 旧版工作线程在 `initEcBacklight` 和 `ecSetBacklightLevel` 前已经释放 `ecLock`，不能构造一个没有证据的“持 ecLock 执行 WMI”的死锁解释。
- v3/v4 已经绕过部分 AMD SET，但仍被报告失败，因此“只把 SET 提前”不足以解释或解决所有症状。
- 此前只读查询日志显示 GET 已成功返回，随后用户报告整机卡住；该库调用读取显示注册表参数，不能仅凭它断言一定执行了本驱动的 AMD GET 包装函数。
- GPU 挂起报告在 EC 关闭时也出现过，不能把所有 GPU 挂起都归因于背光。

当前版本的成功支持重新划分执行边界是可行的实现，但多个结构变化一起生效，不能从这次成功反推出其中唯一一个改变就是旧死机根因。为了归因而重新安装已知失败版逐个恢复旧路径，会再次引入用户已经遭遇的故障；本轮没有这样做。

## 最后修正的依赖为什么重要

旧产物导入 `IOACPIPlatformDevice::metaClass`，实际提供者为 `com.apple.iokit.IOACPIFamily`；声明 `AppleACPIPlatform` 不能替代这项直接依赖。OpenCore 普通符号解析只搜索直接依赖。最终修正后的声明为：

```xml
<key>com.apple.iokit.IOACPIFamily</key>
<string>1.0.0d1</string>
```

这一问题也存在于保存的 v2/v3/v4 产物中。安装回执只证明文件复制完成，不能代替每次启动后的活动驱动及 EC 就绪状态证据；因此早先每轮实机结果的归因都有这一限制。

独立服务重写的第一版另有缺少 `EXPORT` 的问题；Release 隐藏可见性与裁剪会使类元数据符号缺失。补导出后仍启动失败，直到依赖修正后用户确认正常。当前的二进制回归检查同时覆盖类元数据公开性与 ACPI 直接依赖，本机内核集合检查确认该导入符号能够由直接依赖解析。

这最后一项修改解释的是加载失败，不能当作运行时锁问题的证明。现阶段最准确的归纳是：加载错误已修正并得到正常启动反馈，新的 EC 调光路径得到实际亮度变化反馈；旧版整机卡死的唯一具体调用或锁等待仍未被回溯证实。
