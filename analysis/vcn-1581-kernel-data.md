# macOS 15.8.1 kernel VCN bridge data — derivation and evidence

This document is the evidence trail for `NootedRed/VCNKernelData.hpp`, generated by
`tools/gen_vcn_kernel_data.py`. Everything here was derived read-only from this machine's
`/System/Library/KernelCollections/SystemKernelExtensions.kc`; no kernel extension was loaded and no
system file was modified. The report [`analysis/vcn-steve12311.md`](vcn-steve12311.md) was used only as
the semantic map (which objects the native AMDRadeonX6000 VCN2 bridge reuses, which six vtable slots to
guard, which call-site categories to redirect, and the GFXOFF wait pairing). No fork code, header or
generated array was copied; every offset, symbol and byte below was re-derived here and is
machine-checked by `python3 tools/gen_vcn_kernel_data.py --check`.

## 1. Inputs and slice layout

The kernel collection is a fileset Mach-O: top-level load commands contain one `LC_FILESET_ENTRY`
(`0x80000035`) per kext. On this build **the fileset file offset equals the prelink VM address** for
every entry, so the slices can be parsed in place without extracting binaries.

| kext | slice `fileoff`/`__TEXT` VM | `__TEXT` | `__DATA` | `__DATA_CONST` | `__LINKEDIT` |
| --- | --- | --- | --- | --- | --- |
| AMDRadeonX5000 | `0x4357000` | `0x4357000` + `0x224000` | `0x457b000` + `0x32000` | `0x45af000` + `0x5000` | `0x15684000` + `0xd26257` |
| AMDRadeonX6000 | `0xbe39000` | `0xbe39000` + `0x157000` | `0xbf90000` + `0x36000` | `0xbfc7000` + `0x5000` | `0x15684000` + `0xd26257` |

Notes:

- Both kexts share the **same `__LINKEDIT`** at `0x15684000`; their `LC_SYMTAB`s point at different
  symbol-table ranges inside it but at a common string table. The generator reads the shared
  `__LINKEDIT` directly and does not assume per-slice ownership.
- X5000 `__DATA` has `vmsize 0x34000` but `filesize 0x32000` (2 pages of zero fill); all reads used here
  are inside `filesize`.
- Symbol counts in the slices: X5000 4,647; X6000 4,877 (global `N_SECT` symbols).
- The two vtable symbols resolve to:

| table | symbol | address | address point (+2 words) |
| --- | --- | --- | --- |
| X5000 | `__ZTV32AMDRadeonX5000_AMDVega10Hardware` | `0x459c5c0` | `0x459c5d0` |
| X6000 | `__ZTV32AMDRadeonX6000_AMDNavi10Hardware` | `0xbfb5a80` | `0xbfb5a90` |

## 2. Derivation method

The generator is a self-contained Mach-O/kernel-collection reader (no LLVM tools at generation time):

1. Parse the KC header, `LC_FILESET_ENTRY` table and `LC_UUID`.
2. For each AMD slice parse `LC_SEGMENT_64`, `LC_SYMTAB`, `LC_UUID`; build `name -> value` and
   `value -> names` symbol maps from the `N_SECT` symbols.
3. Derive the prelink pointer bias from a semantic anchor: the vtable slot at X5000 `+0x298` is the
   `AMDHardware::isDeviceValid` method, so `bias = stored_pointer(slot) - symbol_address(isDeviceValid)`.
   The same computation on X6000 `+0x2A0` must produce the identical bias (it does:
   `0x40000040000000`). This constant is a property of the kernel-collection relocation format; it is
   **not** used by the runtime bridge, which works with live (slid) pointers.
4. Resolve each guarded vtable slot as `word(table_address_point + slot) - bias`, require it to land in
   `__TEXT`, and for named guards require the target to be exactly the expected method symbol.
5. Extract anonymous getters instruction by instruction, terminating at `pop rbp; ret`, accepting only
   the observed tiny-accessor forms (`push rbp; mov rbp,rsp; <one load>; [and al,1]; pop rbp; ret`) and
   failing on any other opcode/branch/RIP-relative reference.
6. Scan X6000 `__TEXT` for `callq *imm32(%rax)` (`FF 90 <slot32>`) sites whose slot is in the bridge's
   slot map, attribute each site to the enclosing mangled text symbol, apply the bridge's function/slot
   semantics, and require both the hardware-vtable load `movq (%rdi), %rax` (`48 8B 07`) immediately
   before the call and (on the GFXOFF wait paths) the hardware-field receiver load
   (`movq 0x20/0x18(%rdi|%rbx), %rdi`) immediately before that.
7. Assert exact counts (20 patches, 4 GFXOFF wait pairs) so a driver rebuild cannot silently produce a
   partially-redirected patch list.

Reproduction:

```sh
python3 tools/gen_vcn_kernel_data.py          # write NootedRed/VCNKernelData.hpp, print evidence
python3 tools/gen_vcn_kernel_data.py --check  # re-derive + revalidate header, exit 2 on mismatch
```

The generator is deterministic: no timestamps, no environment-dependent ordering, and a second run
produces a byte-identical header.

Findings that matter for the bridge:

1. **The `0x2A8` / `0x2B0` getters are 12 bytes, not 13.** The byte sequence quoted in the prior
   reports (`55 48 89 E5 8A 87 0E 03 00 00 5D C3`) contains 12 bytes; the "13" and the Tahoe reference's
   14-byte form both seem to have been miscounted/assumed. The extra Tahoe bytes are `24 01`
   (`and al, 1`), which **do not exist on 15.8.1**: the 15.8.1 getter returns the raw byte at `+0x30E`.
   `verifyKernelABI()` must therefore match the extracted 12-byte arrays and must not expect an
   `and al,1` guard. (Whether raw-byte vs masked semantics matters to callers is unknown; the guard
   deliberately matches the real binary rather than relaxing.)
2. The two drivers' first getters are byte-identical (`movb 0x30e(%rdi), %al`), but the other two pairs
   read **different field offsets** (`+0x20640` vs `+0x20648`, `+0x20550` vs `+0x20548`). The slots are
   semantically corresponding methods of different object layouts; redirecting X6000 calls to X5000
   slots is exactly what makes the X5000 object's field offsets apply.
3. The getters are headerless tiny accessors; 12/13/12 bytes is the complete function each time, with
   the next function starting immediately after. `getterSize` in the header is derived, not hard-coded.

### 4.2 The four shifted call sites

The fork's Tahoe-generated reference offsets are `setSuspendResumeState +0x27` and
`writeDiagnosisReport +0x524 / +0x7A5 / +0x9B8`. On 15.8.1 the calls exist, but the functions have a
different internal layout, and the enclosing symbols are at different addresses as well. The four
actual offsets are:

| --- | --- | --- | --- |
| `AMDNavi10VideoContext::setSuspendResumeState` | `+0x27` | `+0x28` | `+1` |
| `AMDHWChannel::writeDiagnosisReport` (slot `0x3B0`) | `+0x524` | `+0x52B` | `+7` |

differ, so the reference's `symbol+offset` pairs would not all land on `FF 90` calls anyway; a
version-specific regeneration is required, and the generator asserts that every site still starts with
the expected six bytes and context. The shifted offsets predicted by the earlier read-only spot check
are therefore confirmed.

### 4.3 Submit → signal

`AMDHWChannel::submitCommandBuffer` calls hardware slot `0x230` at `+0x153`. Slot `0x230` does not need
an X5000-slot rewrite: the fork's semantics replace the call with a direct call to
`AMDHardware::signalGPUWorkSubmitted`, which the bridge routes to the X5000
`AMDGFX9Hardware::notifyGfxAccess` so GFXOFF/clocks are handled by the driver that owns the hardware.

- signal symbol: `__ZN26AMDRadeonX6000_AMDHardware22signalGPUWorkSubmittedEv` @ `0xbeac2ee`
- call site: `0xbe853ef`, call end `0xbe853f5`, rel32 displacement `+0x26ef9` (well within ±2 GiB;
  asserted by the generator)
- replacement at runtime: `E8 <rel32> 90` (six bytes, same length as the patched call), computed from
  the live resolved signal address. The header stores only `original` and `newSlot == 0`; the
  displacement is intentionally not baked in.

## 5. Verification performed

1. `python3 tools/gen_vcn_kernel_data.py` — writes the header, prints KC UUID, macOS build, slice
   offsets/segments, versions, SHA-256s, prelink bias, guard targets/getter sizes/displacements, the
   candidate-per-slot counts, all 20 patches and the signal address.
2. `python3 tools/gen_vcn_kernel_data.py --check` — exit 0. It (a) re-derives everything from the KC,
   (b) parses the emitted header's tables/guards/getters/patches independently, (c) re-resolves every
   guard slot and `memcmp`s every getter and patch original against the KC, (d) re-checks the
   `newSlot` consistency, the 6/6/20 counts and the KC UUID, and (e) byte-compares the header with a
   fresh rendering.
3. Negative tests (all exit 2 with a specific error): missing header, a flipped getter byte, a stale
   patch offset, and a changed `SourceDescription` string.
4. Determinism: two independent generator runs produce a byte-identical header.
5. Cross-check with LLVM tools on a read-only thin Mach-O reconstructed from the slice (scratch only, in
   `/tmp`): `llvm-nm -n` reports the same symbol addresses used here (e.g.
   `0xbe8529c __ZN27AMDRadeonX6000_AMDHWChannel19submitCommandBuffer…`, `0xbeac2ee
   __ZN26AMDRadeonX6000_AMDHardware22signalGPUWorkSubmittedEv`, `0xbe89922
   __ZN26AMDRadeonX6000_AMDHWEngine11waitForIdleEj`); `llvm-objdump` confirms each getter and each
   patch context shown above.
6. Header syntax check: `clang++ -std=c++23 -fsyntax-only -isysroot <CLT SDK> -I NootedRed` on a
   translation unit that includes `<VCNKernelData.hpp>` and `static_assert`s the getter sizes, 6 guards
   per side and 20 patches — passes. (No `xmake` build was run, per task rules.)

## 6. Header contract and runtime obligations

`NootedRed/VCNKernelData.hpp` exports (namespace `VCNKernelData`, `<IOKit/IOTypes.h>` types only, all
`inline constexpr`, no dynamic initialisation, no STL):

- `CallPatch { const char* symbol; UInt32 offset; UInt8 original[6]; UInt32 newSlot; }` × 20 in
  `CallPatches[]`.
- `SlotGuard { UInt32 slot; const char* methodSymbol; const UInt8* getter; UInt32 getterSize; }` × 6 in
  each of `Guards5000[]` / `Guards6000[]`; `nullptr` method + getter for anonymous slots.
- `Getter5000_1/2/3`, `Getter6000_1/2/3`, `Table5000`, `Table6000`, `SignalSymbol`,
  `SourceDescription`, `KernelCollectionUUID`, `DriverUUID5000/6000`, `DriverVersion5000/6000`,
  `DriverSHA256_5000/6000`.

The bridge is expected to:

1. Verify the loaded driver identity (versions/UUIDs/hashes) before installing anything.
2. Resolve the vtable symbols with the kernel's symbol lookup and validate all six guards per driver by
   method-symbol identity / full getter byte comparison. Note that the anonymous getters are exact
   12/13/12-byte functions on 15.8.1; a Tahoe-style 14-byte getter with `and al,1` will not match.
3. Verify all 20 `original` byte sequences before patching any of them (all-or-nothing), and restore
   them on failure/rollback. `newSlot == 0` means write `E8 rel32 90` to the live `SignalSymbol`.
4. Between the X6000 module write-scope and this data: avoid re-deriving offsets at runtime; if any
   `original` does not match, abort the bridge and leave the native graphics state untouched.

## 7. Assumptions, scope limits and unknowns

- **Semantic map, not data, came from prior art.** The categories and six-slot guard set are from
  [`analysis/vcn-steve12311.md`](vcn-steve12311.md); all values are from this KC. No fork header/code
  was read into the generator or copied into the tree.
- **Symbol visibility at runtime is unverified.** The patch symbols are present in the KC symbol table;
  whether `KernelPatcher`/`kallsyms` exposes every X6000 private symbol on 15.8.1 (so the bridge can
  resolve them) is a Phase-2 runtime validation item, not proven here.
- **Patch scope.** Only `callq *imm32(%rax)` sites in `AMDHWChannel`, `AMDVCN2HWEngine::isIdle`,
  `AMDNavi10VideoContext::setSuspendResumeState` and the two `waitForIdle` paths are redirected. Other
  X6000 hardware-call sites (`AMDDMAHWChannel`, `AMDPM4HWChannel`, `AMDVCNHWChannel`,
  `AMDVCNHWEngine`, `AMDGFX10*` classes, etc.) exist in the same binary and are deliberately excluded:
  they are not part of the fork's validated bridge object model. If the native X6000 path instantiates
  a subclass whose method override bypasses `AMDHWChannel`, this set may need extending — that is a
  runtime-validation question.
- **Anonymous-slot semantics are inferred, bytes are exact.** The six guarded slots correspond to the
  fork's conceptual `isDeviceValid`, three getters, `disableGfxOff`, `enableGfxOff` set; the guard bytes
  are the ground truth and make a mismatched layout fail closed.
- **Getter return semantics changed on 15.8.1**: the `+0x30E` getter returns the raw byte instead of a
  masked 0/1. Whether callers tolerate non-0/1 values is unknown; the bridge should not relax the
  guard, and any consumer that needs a boolean must normalise it.
- **Prelink bias is a generation-time aid only.** The runtime bridge must use live pointers; the
  `0x40000040000000` constant is not exported in the header.
- **Submit rewrite assumes instruction boundaries**: the `0x230` call is a 6-byte instruction and no
  code branches into its immediate (verified by the layout of the enclosing function); the rewrite is
  same-length and does not need instruction-cache-safe block movement beyond the usual kernel text
  write handling.
- **Not covered here:** user-space `AMDRadeonVADriver2`/AppleGVA data (separate task), firmware/PSP
  behaviour, engine allocation offsets (separate code task), and any hardware validation. This
  deliverable is data plus its derivation only.
